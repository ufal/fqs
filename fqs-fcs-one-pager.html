FQS as a multi-engine CLARIN FCS endpoint

FlexiCorp Query Server (FQS) is the institutional front door for corpus search: one HTTP service, one corpus catalogue, and—when finished—one CLARIN Federated Content Search (FCS / SRU) URL that can answer aggregator and client queries against corpora backed by Manatee, CWB (CQP), BlackLab, or Pando. Clients never talk to those engines directly; FQS owns protocol, policy, and result shape.

What the client sees

A single FCS base URL (e.g. https://query.example.org/fcs) implements the usual SRU operations:

OperationRole
explainAdvertises FCS-enabled resources (PID, title, languages, capabilities)
searchRetrieveRuns a query and returns hits/KWIC in FCS/SRU XML
scan(Completed design) term/value browsing where a backend supports it

Corpus selection uses FCS context (x-fcs-context / resource PID). With no context, FQS can search all policy-eligible, FCS-enabled corpora and merge summaries—useful for institute-wide discovery.

One catalogue, many engines

Each publication (corpus + content version) is one catalogue row—not one row per engine. The row carries:

  • paths / connection settings for whichever index exists
  • preferred_backend (pando | cqp / Manatee | blacklab | auto)
  • capabilities.fcs (enabled, resource_pid, dataviews, caps)

Manatee, CWB, BlackLab, and Pando are execution backends, not separate FCS endpoints. Turning FCS on is a catalogue flag plus policy (public / capped / login-gated), independent of the TEITOK UI.

Request path (completed FQS)

FCS client / CLARIN aggregator
        │  SRU/FCS XML
        ▼
   FQS  /fcs
        │  1. Resolve resource → catalogue entry + policy
        │  2. Translate FCS-QL → backend dialect
        │  3. Dispatch to warm backend pool
        │  4. Normalise hits → FCS XML (hits / KWIC dataviews)
        ▼
   Manatee │ CWB/CQP │ BlackLab │ Pando
  1. Protocol — Parse SRU parameters; enforce FCS-enabled and result caps (often stricter for anonymous FCS than for logged-in UI users).
  2. Translate — Map a documented FCS-QL subset into the dialect of the selected backend (Manatee-CQL, CWB-CQL, BCQL, Pando-CQL). Unsupported constructs fail clearly rather than silently degrading.
  3. Execute — Reuse the same warm-pool path as the native JSON API (LRU-warm processes/handles per corpus; no per-request cold CLI spawn).
  4. Serialise — Map engine hits into a common internal hit model, then into FCS XML so aggregators see one shape regardless of engine.

Native /query JSON and /fcs XML therefore share catalogue, auth/policy, and backends; only the wire format differs.

Why this works across engines

ConcernHandled by
“Is this corpus in FCS?”Catalogue capabilities.fcs
“Which engine runs it?”preferred_backend / auto + settings
“What may an external client see?”FQS policy + FCS result caps
“How do aggregators discover us?”explain (+ optional EndpointDescription)
“Do clients learn Manatee vs Pando?”No — only FQS and FCS-QL

Institutes can expose a mixed estate (legacy Manatee/CWB, BlackLab, new Pando) under one FCS registration, without rewriting aggregator config when a corpus migrates engine.

Status toward “completed”

Already sketched / partially live: /fcs with explain / searchRetrieve, catalogue FCS metadata, policy hooks, and a shared query path (Pando-first; CQP path exists).

To finish the multi-engine story: production adapters for Manatee and BlackLab on the same pool; fuller FCS-QL→dialect translation; robust scan; stable PIDs and caps for aggregator use; optional Mode A (central institute FQS) vs Mode B (per-project PHP shim) deployment.

In one line: FQS is the FCS endpoint; Manatee, CWB, BlackLab, and Pando are pluggable indexes behind a shared catalogue and a shared SRU façade.
